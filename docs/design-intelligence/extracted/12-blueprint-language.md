# Purpose

Blueprint visualizes understanding.

Unlike Office, which visualizes execution, Blueprint visualizes the structure behind execution.

Users should understand

How work flows

Why decisions exist

How artifacts depend on one another

Which agents contribute

What the current lifecycle state means

Blueprint should answer

"How does this Product Operating System think?"

---

# Blueprint Philosophy

Blueprint is a living knowledge graph.

Not a static diagram.

Not documentation.

Not an illustration.

The graph evolves together with the project.

Every interaction should increase understanding.

---

# Edge Philosophy

Edges explain relationships.

Edges should always answer

Why are these two things connected?

Relationship types include

Creates

Depends On

Reviews

Generates

Approves

Blocks

References

Updates

Each relationship should have clear semantics.

# Reading Direction

Blueprint should encourage a consistent reading flow.

Preferred direction

Left

↓

Right

following lifecycle progression.

Secondary relationships may branch vertically.

Avoid circular layouts unless representing true cycles.

# Blueprint Quality Checklist

Before approving Blueprint ask

[ ] Can users understand the lifecycle within five seconds?

[ ] Are dependencies understandable?

[ ] Does zoom reveal information rather than simply enlarge graphics?

[ ] Are relationships meaningful?

[ ] Can users investigate any node without leaving Blueprint?

[ ] Does the graph preserve orientation?

[ ] Does Blueprint increase understanding instead of complexity?

---

# Non-Negotiables

Never create decorative graphs.

Never sacrifice comprehension for visual density.

Never rearrange nodes unpredictably.

Never hide critical dependencies.

Blueprint exists to explain the Product Operating System.
