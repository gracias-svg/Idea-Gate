# Purpose

Visualization exists to simplify complexity.

Every visual element should help users understand relationships, progress, dependencies, risk, or structure.

Users should never look at a visualization and ask,

"What am I supposed to learn from this?"

---

# Design Philosophy

Visualizations should feel

Clear

Analytical

Editorial

Elegant

Professional

Trustworthy

Avoid

Decorative charts

3D effects

Excessive gradients

Bright colors

Chart junk

Visual noise

---

# Core Principles

## Principle 1

Every visualization answers one question.

Examples

Progress

Dependency

Relationship

Timeline

Risk

Coverage

Flow

Ownership

Never combine multiple unrelated questions into one visualization.

---

## Principle 2

Visualization supports decisions.

Every graph should influence user action.

If a visualization cannot change a decision, reconsider including it.

---

## Principle 3

Text and visuals work together.

Charts summarize.

Text explains.

Neither should replace the other.

# Visualization Categories

## Lifecycle Visualization

Purpose

Explain stage progression.

Examples

Current stage

Completed stages

Blocked stages

Pending stages

Users should immediately understand where the project stands.

---

## Dependency Graph

Purpose

Reveal relationships.

Examples

Artifacts

Research

Architecture

UX

Backlog

QA

Prototype

Nodes should communicate dependency strength.

Critical paths should receive visual emphasis.

---

## Timeline

Purpose

Communicate sequence.

Use for

History

Versions

Reviews

Iterations

Approvals

Timelines should scroll naturally and preserve chronology.

---

## Flow Diagrams

Purpose

Explain processes.

Examples

Agent workflow

Lifecycle execution

Artifact generation

Decision pipeline

Connections should minimize unnecessary crossings.

Reading direction should remain consistent.

---

## Progress Indicators

Progress should always communicate

Completion

Current activity

Remaining work

Estimated next milestone

Avoid meaningless percentage bars without context.

---

## Health Indicators

Health combines multiple signals.

Examples

Execution quality

Blocked work

Confidence

Coverage

Artifact completeness

Health should never depend on a single metric.

---

## Risk Visualization

Highlight

Critical blockers

Dependency failures

Low confidence

Missing artifacts

Failed validation

Risk should be immediately distinguishable from informational content.

---

## Relationship Maps

Relationship maps should answer

What influences what?

Examples

Research → PRD

PRD → UX

UX → Architecture

Architecture → QA

Dependencies should feel directional.

---

## Comparison Views

Comparisons should emphasize differences.

Not similarities.

Examples

Version comparison

AI improvement

Document revisions

Research evolution

Highlight changes before displaying unchanged content.

---

## AI Reasoning Views

Reasoning should be visualized as a structured decision flow.

Recommendation

↓

Evidence

↓

Assumptions

↓

Trade-offs

↓

Confidence

↓

Outcome

Avoid large walls of reasoning text.

# Labels

Every visualization requires

Title

Purpose

Units

Legend (if necessary)

Context

Source

Never assume users understand visual encoding.

---

# Color Strategy

Color communicates state.

Never structure.

Recommended

Success

Warning

Risk

Neutral

Selection

Active

Inactive

Avoid assigning arbitrary colors to categories.

---

# Animation

Visualizations should animate only when

Data changes

Relationships change

Nodes appear

Progress updates

Never animate continuously.

---

# Interaction

Users should be able to

Hover

Inspect

Filter

Expand

Collapse

Trace dependencies

Open related artifacts

Interactions should reveal depth without clutter.

---

# Empty States

Instead of

"No data"

Prefer

"No dependency relationships have been established yet."

Guide users toward the next action.

---

# Quality Checklist

Before approving any visualization ask

[ ] Does it answer one clear question?

[ ] Can users understand it within five seconds?

[ ] Does it support a decision?

[ ] Is visual noise minimized?

[ ] Does animation reinforce understanding?

[ ] Are labels sufficient?

[ ] Would removing the visualization reduce understanding?

If not, remove it.

---

# Non-Negotiables

Never visualize data simply because it exists.

Never prioritize aesthetics over comprehension.

Never overload users with charts.

Every visualization should improve product thinking.
